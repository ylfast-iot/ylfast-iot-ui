# AgileFast Web 前端接口对接规范

## 1. 适用范围

本文适用于 `ylfast-iot-ui/apps/xx` 的前端接口开发与对接，重点约束以下内容：

- `src/api/**/*.ts` 的组织方式
- 与后端接口的字段映射方式
- 基于 `buildBasicCrudApis` 的通用 CRUD 对接方式
- 基于 `QueryParamEntity` 的动态查询参数传递方式

本文不是脱离项目上下文的通用前端 API 规范，而是基于当前工程实际封装方式整理。

## 2. 核心参考

推荐优先阅读以下文件：

- `ylfast-iot-ui/apps/ylfast-iot-platform/src/api/basic.ts`
- `ylfast-iot-ui/apps/ylfast-iot-platform/src/adapter/crud/QueryParams.ts`

## 3. API 文件落位规范

接口文件统一放在：

```text
apps/ylfast-iot-platform/src/api/{domain}/
```

推荐按业务域分目录：

- `src/api/system`
- `src/api/wms`
- `src/api/railway`
- `src/api/examples`

新增一个 CRUD 资源时，优先一个资源一个接口文件，不要把多个无关资源混写到同一个文件里。

## 4. 命名规范

### 4.1 namespace 命名

统一使用：

```ts
export namespace XxxApi {}
```

示例：

```ts
export namespace CrudDemoArticleApi {}
```

### 4.2 实体接口命名

资源实体统一命名为：

```ts
Xxx;
```

示例：

```ts
export interface CrudDemoArticle extends BasicEntity<string> {
  title: string;
}
```

### 4.3 自定义接口常量命名

资源内的特殊接口统一放在 `Apis` 常量中：

```ts
export const Apis = {
  test: `${BASE_URL}/test`,
};
```

## 5. 通用 CRUD 对接规范

### 5.1 优先复用 `buildBasicCrudApis`

对于后端已经接入 `ServiceCrudController` 的资源，前端统一优先使用：

```ts
buildBasicCrudApis<E, K>(BASE_URL);
```

示例：

```ts
export const basicCrudApis = buildBasicCrudApis<CrudDemoArticle, string>(
  BASE_URL,
);
```

说明：

- `buildBasicCrudApis` 现在同时封装了物理删除和逻辑删除接口
- 如果后端资源已经继承 `ServiceCrudController`，前端不要再单独手写 `logicDeleteById`、`logicDeleteBatch`
- 特殊业务删除动作才放到资源自己的 `Apis` 中单独维护

### 5.2 `BASE_URL` 规范

`BASE_URL` 必须与网关真实暴露路径保持一致，不要凭空补前缀或删前缀。

当前 CRUD 示例使用：

```ts
const BASE_URL = '/crud-demo/articles';
```

注意：

- 同一业务资源内必须保持一致
- 不要同一个文件里一部分接口用 `/api/...`，另一部分用裸路径

### 5.3 `BasicEntity` 继承规范

通用 CRUD 资源实体统一继承：

```ts
BasicEntity<string>;
```

当前项目里，通用 CRUD 示例主键默认为 `string`，并继承通用审计字段：

- `id`
- `creatorId`
- `creatorName`
- `createTime`
- `modifierId`
- `modifierName`
- `modifyTime`

## 6. CRUD 接口与前端调用映射

`buildBasicCrudApis` 当前对接的标准接口如下：

| 前端方法 | 后端接口 | 用途 |
| --- | --- | --- |
| `deleteById(id)` | `DELETE /{id}` | 单个物理删除 |
| `deleteBatch(ids)` | `DELETE /_batch` | 批量物理删除，请求体传 ID 数组 |
| `logicDeleteById(id)` | `DELETE /logic/{id}` | 单个逻辑删除（暂未实现） |
| `logicDeleteBatch(ids)` | `DELETE /logic/_batch` | 批量逻辑删除，请求体传 ID 数组（暂未实现） |
| `patchSave(data)` | `PATCH /` | 保存，存在则覆盖，不存在则新增 |
| `postInsertBatch(data)` | `POST /_batch` | 批量新增 |
| `postAdd(data)` | `POST /` | 新增单条 |
| `putUpdate(id, data)` | `PUT /{id}` | 按 ID 更新 |
| `getById(id)` | `GET /{id}` | 按 ID 查询 |
| `getQuery(params)` | `GET /_query` | GET 分页查询 |
| `postQuery(params)` | `POST /_query` | POST 分页查询 |
| `getQueryNoPaging(params)` | `GET /_query/no-paging` | GET 不分页查询 |
| `postQueryNoPaging(params)` | `POST /_query/no-paging` | POST 不分页查询 |
| `getCount(params)` | `GET /_count` | 统计数量 |
| `postCount(params)` | `POST /_count` | 统计数量 |
| `getExists(params)` | `GET /_exists` | 判断是否存在 |
| `postExists(params)` | `POST /_exists` | 判断是否存在 |

## 7. 分页结果规范

前端表格统一消费：

```ts
interface PagerResult<T> {
  total: number;
  result: T[];
}
```

因此前端分页查询不要自行再做一套新结构。

## 8. QueryParamEntity 规范

动态查询统一使用 `QueryParamEntity`，定义在：

```text
apps/ylfast-iot-platform/src/adapter/crud/QueryParams.ts
```

常用字段：

- `pageIndex`
- `pageSize`
- `paging`
- `terms`
- `sorts`
- `where`
- `orderBy`
- `includes`
- `excludes`
- `total`

推荐规则：

- 简单条件搜索优先用 `terms`
- 页面分页查询统一传 `pageIndex`，并从 `0` 开始
- 默认排序统一传 `sorts`
- 列表页面优先使用 `POST /_query`

示例：

```ts
const queryParams: QueryParamEntity = {
  pageIndex: page.currentPage - 1,
  pageSize: page.pageSize,
  terms: formValues.terms,
  sorts: [{ name: 'createTime', order: 'desc' }],
};
```

## 9. 自定义接口规范

如果某个资源除了标准 CRUD 还有特有动作：

1. 资源内定义 `Apis`
2. 资源内单独导出方法
3. 自定义接口不要混进 `basicCrudApis`

示例：

```ts
export const Apis = {
  test: `${BASE_URL}/test`,
};

export function testArticle() {
  return requestClient.get(CrudDemoArticleApi.Apis.test);
}
```

### 9.1 返回 `Void` 的写法约束

如果后端接口返回 `Void`，前端对接时不要写：

```ts
requestClient.post<void>(url, data);
requestClient.put<void>(url, data);
requestClient.patch<void>(url, data);
requestClient.delete<void>(url);
```

统一改为：

```ts
requestClient.post(url, data);
requestClient.put(url, data);
requestClient.patch(url, data);
requestClient.delete(url);
```

原因：

- `Void` 返回值不提供有效类型信息
- 统一省略泛型更符合当前项目既有对接风格
- 可以减少无意义的类型噪音

## 10. 字段映射规范

前端类型字段必须与后端实体保持一致。

同时必须遵守以下注释约束：

- `interface`、`type`、`namespace` 中的业务属性必须补充简洁中文注释
- 注释要直接说明字段业务语义，不要写无意义注释
- 对后端直传字段，优先按后端语义写注释，不要自行发明新含义

以 `CrudDemoArticleEntity` 为例，前端接口模型应至少包含：

- `title`
- `category`
- `author`
- `content`
- `status`
- `sort`
- `remark`

如果后端新增了业务字段，前端需要同步更新三处：

1. `src/api/...` 中的实体接口
2. `views/.../data.tsx` 中的表格和表单 schema
3. `views/.../components/*.vue` 中的展示组件

## 11. 示例模板

```ts
import { buildBasicCrudApis, type BasicEntity } from '#/api/basic';
import { requestClient } from '#/api/request';

export namespace BizExampleApi {
  export interface BizExample extends BasicEntity<string> {
    name: string;
    status?: number;
    remark?: string;
  }

  const BASE_URL = '/biz/examples';

  export const Apis = {
    sync: `${BASE_URL}/sync`,
  };

  export const basicCrudApis = buildBasicCrudApis<BizExample, string>(BASE_URL);
}

export function syncBizExample() {
  return requestClient.post(BizExampleApi.Apis.sync);
}
```

## 12. 禁止事项

- 不要在页面里直接拼接请求 URL 字符串
- 不要跳过 `src/api` 直接在 `vue` 文件里写 `requestClient`
- 不要前端自造一套与后端不一致的字段名
- 不要把分页结构写成 `list/totalCount`，同时又在别处写成 `items/total`
- 不要在同一资源内混用多套路径前缀规范
- 不要给返回 `Void` 的接口显式写 `requestClient.<void>`
- 不要省略导出接口方法的注释，所有导出方法都应补简洁中文注释
- 不要省略接口类型属性注释，所有业务属性都应补简洁中文注释

## 13. 当前推荐结论

对接新的通用 CRUD 资源时，推荐统一采用以下组合：

- `src/api/{domain}/xxx.ts`
- `namespace + interface + Apis + basicCrudApis`
- 实体类型继承 `BasicEntity<string>`
- 查询参数统一使用 `QueryParamEntity`
- 页面分页统一消费 `{ items, total }`
- 特殊接口与标准 CRUD 接口分开维护
- 标准删除与逻辑删除优先复用 `basicCrudApis`
