# 场景联动旧版实现对照与新版改造说明

## 1. 背景

当前 `apps/ylfast-iot-platform/src/views/iot/rule-engine/scene` 的新版实现，已经完成了基础接口对接和部分详情页编辑能力，但整体交互模型仍偏“表单页 + JSON 配置”，与旧版 `jetlinks-ui-vue` 中场景联动的真实工作台形态不一致。

用户明确要求新版对齐旧版实现思路，因此本次需要先分析旧版，再按旧版的入口链路、页面结构、规则模型和组件拆分方式重构当前页面。

## 2. 旧版实现结论

旧版参考代码位置：

- `D:/projects/DataHole/jetlinks/mo-di-he/jetlinks-ui-vue/src/modules/rule-engine-manager-ui/views/Scene`
- `D:/projects/DataHole/jetlinks/mo-di-he/jetlinks-ui-vue/src/modules/rule-engine-manager-ui/views/Scene/Save`

### 2.1 列表页不是直接进入“大表单新增”

旧版列表页的新增行为分两步：

1. 先弹出一个轻量新增弹窗 `Save/save.vue`
2. 只填写 `名称 + 触发方式`
3. 先调用后端创建场景壳数据
4. 创建成功后再跳转到完整的 `Save/index.vue` 工作台继续配置

这个链路的价值是：

- 详情页永远工作在一个已经存在的场景实体上
- 后续动作、分支、变量解析、告警解绑等操作都能基于真实 `id` 工作
- 新增和编辑共用同一个详情工作台

### 2.2 详情页不是 Tab 表单，而是规则工作台

旧版 `Save/index.vue` 的核心结构是：

- 顶部标题区：名称、触发类型、描述
- 中部整页表单容器
- 根据 `triggerType` 渲染不同的触发器模块
- 触发器模块下面直接衔接动作编排
- 页面底部统一保存

它不是“基础信息 / 触发器 / 动作”三个 Tab，而是一条连续的规则配置流。

### 2.3 详情页按触发类型拆成独立模块

旧版会按触发器类型拆出不同模块：

- `Device/index.vue`
- `Manual/index.vue`
- `Timer/index.vue`
- `Collector/index.vue`

这几个模块共享同一个场景数据模型，但各自负责：

- 触发规则配置
- 分支条件编辑
- 串行 / 并行动作区编排

这说明旧版的核心设计不是“一个通用大组件兼容全部”，而是“页面壳 + 触发类型专属实现”。

### 2.4 设备触发场景是完整的规则工作台

从旧版设备触发界面可以确认它包含以下层次：

1. 触发规则
2. 执行动作
3. `当` 分支
4. `否则` 分支，可继续新增
5. 每个分支下又有：
   - 分支条件
   - 执行开关
   - 防抖 / 抑制相关配置
   - 串行区
   - 并行区
6. 每个动作后还可以配置“满足此条件后执行后续动作”

这说明旧版并不是简单的“动作列表”，而是：

- 分支级条件
- 动作组级串并行
- 动作级后续条件

三层结构同时存在。

### 2.5 旧版有自己的场景专用数据模型和状态仓库

旧版并没有直接把后端返回结构硬塞到页面里，而是配套了：

- `views/Scene/typings.ts`
- `views/Scene/Save/util.ts`
- `store/scene.ts`

这些文件负责：

- 前端专用类型定义
- 默认分支和默认动作结构
- key 分配
- 触发器和动作的前端显示态数据
- `features` 计算
- 页面离开前脏数据检测

这意味着旧版的成功关键在于：

- 有一层场景专用前端模型
- 页面组件都围绕这层模型工作

而不是直接把接口模型当作页面模型。

## 3. 当前新版与旧版的关键差异

当前新版已经完成的部分：

- 后端接口已从 `Recordable` 改为真实类型
- 列表页已有新增弹窗
- 详情页已具备保存能力

但和旧版仍有明显差异：

### 3.1 详情页结构偏表单，不是工作台

当前详情页偏向：

- 基础表单
- 触发器字段
- 动作字段

而旧版是：

- 场景壳 + 触发规则 + 分支 + 串并行动作 + 动作后续条件

### 3.2 过度依赖 JSON 文本输入

当前新版大量字段仍通过 JSON 文本编辑：

- 触发器配置
- 设备选择值
- 函数参数
- 动作过滤条件

这虽然能工作，但与旧版可视化工作台差异太大，也不利于业务配置。

### 3.3 通用条件表单与规则工作台不匹配

当前仓库已有 `yl-dc-form`，它更适合“搜索条件表单”。

而旧版场景联动条件编辑的特点是：

- 条件是规则流的一部分
- 条件与动作顺序强关联
- 条件需要嵌在分支和动作之间
- 视觉上是规则编排，而不是搜索面板

因此单纯复用 `yl-dc-form` 会产生交互错位。

## 4. 本次改造决策

### 4.1 保留旧版的入口链路

新版列表页改成与旧版一致：

1. 列表新增先弹轻量弹窗
2. 创建场景壳成功后直接跳详情页
3. 详情页统一承接后续配置

### 4.2 详情页改成“场景工作台”

新版详情页不再使用“基础信息 / 触发器 / 动作”式的 Tab 结构，而改成：

- 顶部标题区
- 触发规则区
- 执行动作区
- 分支工作台

### 4.3 重新编写场景专用条件组件

本次不再直接套 `yl-dc-form`，而是新增场景专用条件组件，原因：

- 旧版交互是规则编排，不是搜索
- 条件要支持 `当 / 否则 / 动作后续条件`
- 条件编辑要能内嵌在分支卡片和动作链里
- 需要围绕 `parseSceneTermColumns` 和 `parseSceneVariables` 做动态列解析

新条件组件的设计目标：

- 面向规则流而不是搜索表单
- 支持条件组和组内条件
- 支持列、操作符、值的联动
- 支持以触发列和动作变量两种数据源驱动

### 4.4 继续遵循 TSX + 单一职责拆分

复杂组件统一使用 TSX，并拆分到独立子组件，避免 `detail.vue` 变成巨石文件。

推荐职责划分：

- `detail.vue`：页面编排、数据加载、保存
- `SceneDetailHeader.tsx`：顶部标题区
- `SceneTriggerSection.tsx`：触发规则区
- `SceneBranchEditor.tsx`：分支工作台
- `SceneConditionEditor.tsx`：场景专用条件编辑器
- `SceneActionConfigModal.tsx`：动作配置弹层

## 5. 本次新版对齐范围

本次重构优先对齐以下关键能力：

1. 新增弹窗创建后跳详情页
2. 详情页改成工作台布局
3. 设备触发按旧版结构呈现
4. 支持 `当 / 否则` 分支
5. 支持串行 / 并行动作区
6. 重写场景专用条件组件
7. 动作条件改为结构化编辑，不继续只靠 JSON 文本

本次不强求一步做到与旧版 100% 等价的点：

- 旧版全部 provider 的高级动作渲染
- 旧版全部防抖、抑制、执行策略细节
- 告警解绑、离页脏数据比对等二阶行为

这些能力可以在新版工作台结构稳定后继续补齐。

## 6. 风险说明

### 6.1 当前 `scene` 页面已有一轮实现，需要重构而不是修补

这次不是简单改几处样式，而是把页面从“表单页”改回“规则工作台”。继续在旧实现上打补丁会让结构越来越脆弱，因此应直接重构。

### 6.2 条件组件必须独立，否则 detail 页会再次膨胀

场景条件、动作条件、变量条件都收敛在一个巨型页面里，会很快形成新的坏味道：

- 僵化
- 晦涩性
- 不必要复杂性

因此条件编辑器必须抽离。

## 7. 结论

旧版场景联动的核心不是“字段多”，而是“规则工作台模型”。

新版需要对齐的重点不是把旧版所有 UI 像素复刻，而是把以下三件事恢复回来：

1. 场景壳先创建，再进入详情工作台
2. 详情页按触发类型组织规则工作台
3. 条件与动作围绕分支结构进行编排

本次改造会按这个方向重构当前 `scene` 模块。

## 8. 本轮已完成的旧版对齐点

本轮已进一步把新版向旧版设备触发工作台收敛，具体包括：

### 8.1 设备触发入口改回“摘要按钮 + 配置弹层”

旧版 `Save/Device/index.vue` 的核心不是直接把 `productId / selector / operator / JSON` 平铺在页面上，而是：

1. 页面中显示一个触发摘要入口
2. 点击后打开 `AddModal.vue`
3. 在弹层里按步骤完成配置
4. 保存后回填到工作台

新版当前也已改为这个结构：

- 页面只保留“已配置设备触发 / 点击配置设备触发”的摘要按钮
- 触发产品、设备范围、触发方式都放到 `SceneDeviceTriggerModal.tsx`
- 保存时才一次性回填到 `state.trigger`

### 8.2 设备触发弹层对齐旧版三步流

当前 `SceneDeviceTriggerModal.tsx` 已按旧版思路拆成三步：

1. 选择产品
2. 选择设备范围
3. 配置触发方式

并保留了旧版最关键的逻辑：

- 先选产品，后续步骤依赖该产品
- 固定设备模式下可直接选择设备
- 固定设备只选中一个设备时，优先取设备自身物模型
- 否则回退使用产品物模型
- 触发方式按物模型能力动态决定可选项

### 8.3 保存前增加触发器完整性校验

旧版设备触发在表单项上有明确校验，新版这一轮也补齐了保存前校验，避免保存出不完整规则：

- 未选产品不能保存
- 固定设备 / 组织范围未选值不能保存
- `readProperty` 未选属性不能保存
- `writeProperty` 未配置属性值不能保存
- `invokeFunction` 未选功能不能保存
- `reportEvent` 未选事件不能保存

### 8.4 当前仍未完全对齐旧版的点

本轮还没有完全做到旧版等价的部分主要有：

- 旧版 `Type.vue` 中更细的物模型参数可视化编辑
- 旧版 `Terms` 系列组件那种更强规则流视觉
- 旧版动作项里更完整的 provider 专属展示
- 防抖、抑制、执行策略等二阶配置

这些会继续沿着“旧版逻辑优先、TSX 复杂组件拆分、detail 页面只做编排”的方向补齐。
